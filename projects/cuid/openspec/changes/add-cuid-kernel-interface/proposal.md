## Why

Fleet management, profiling and debug tooling has no stable way to name a
physical AMD component. PCI BDF changes when the topology changes, DRM render
node numbers change across boots, and the PCIe Device Serial Number is a raw
hardware serial that cannot be handed to unprivileged software. The CUID
specification (S1, Blinzer) defines a Component Unified ID: a 122-bit payload
rendered as an RFC 9562 UUIDv8, plus an HMAC-derived value that names the same
component without disclosing its serial.

The kernel is the only component that can read the privileged identity, so it
has to be the authoritative source. `amdgpu` gets a sysfs interface that
publishes it, and the userspace CUID library consumes that interface instead of
recomputing everything itself — which is what let the two layers silently
diverge until cross-layer verification on two W6800s forced them back together.

This change is the first upstream posting of that interface. It is scoped
deliberately narrowly: the parts of the specification that are settled, and
nothing that is still under discussion.

## What Changes

- Add a driver-independent CUID core (`cuid_ident` in, `struct cuid` embedded by
  the caller) that packs the 122-bit primary payload, frames it as UUIDv8 and
  derives the secondary value by HMAC-SHA256.
- Add three sysfs attributes on the PCI device: `cuid_primary` (0400 +
  `CAP_SYS_ADMIN`), `cuid_secondary` (0444) and `cuid_seed` (0600 +
  `CAP_SYS_ADMIN`).
- Register the group from `amdgpu` with component type GPU, and document all of
  it in `Documentation/ABI/testing/sysfs-driver-amdgpu-cuid`.
- Log the primary→secondary association with `dev_info()` on every seed change,
  satisfying S1's requirement that the association is tracked "with a timestamp
  in a log".
- **BREAKING (pre-upstream, against the current out-of-tree branch)** Remove
  `cuid_temporary` and the whole in-kernel auxiliary/fallback path
  (`cuid_aux_serial()`, the `aux` argument threaded through `cuid_pack()`, the
  DMI/SMBIOS lookup). Paul settled on 2026-08-20 that the auxiliary CUID is
  generated by **user-mode software only**, as a last resort when kernel
  infrastructure is absent. Where the kernel has a serial it builds a genuine
  primary and never falls back; where it does not, it must publish nothing
  rather than an ambiguous value. This also disposes of the standing objection
  that a kernel driver cannot read `/etc/machine-id` — no kernel component was
  ever meant to.
- Fix bit 117 as the Auxiliary Value Identifier in both the primary and the
  derived layout, permanently borrowed from UnitID part 2, so UnitID part 2 is
  `112:116` and the derived hash slice is `hash[64:108]` (45 bits). The kernel
  never sets bit 117; it is reserved for the library's auxiliary values.

## Capabilities

### New Capabilities
- `cuid/identifier-format`: the wire format — the 122-bit primary payload
  layout, component type numbering, RFC 9562 UUIDv8 framing and octet order, and
  the HMAC-SHA256 derivation of the secondary payload. This is a frozen ABI
  shared with the userspace CUID library; it is specified here so that a
  divergence between the two layers is a spec violation rather than a surprise.
- `cuid/sysfs-interface`: the kernel-side contract — attribute names, values,
  permissions and privilege gating, seed provisioning and lifecycle, the
  association log, and the conditions under which the group is registered at
  all.

### Modified Capabilities

_None. `openspec/specs/` records the published specification as a baseline, and
every repair to it is owned by `amend-published-cuid-spec`. Both capabilities
above are new._

### Where this change can and cannot be checked

The code this change describes lives in the kernel tree, not in
`rocm-systems`. From this repository, `cuid/identifier-format` is checkable in
full — the conformance vectors in `pin-cuid-cross-layer-contract` are the
kernel's own values, generated by `tests/vectors/cuid_vectors.py`, asserted
against the library by `tests/unit/vectors_test.cc`, and held byte-identical to
the kernel's copy by the drift check in `.github/workflows/cuid-workflow.yml`.
`cuid/sysfs-interface` is **not** checkable here: the attribute names, modes,
capability checks, seed length handling, association logging and teardown
behaviour are all statements about `amdgpu_cuid.c`, and nothing in this tree
exercises them. What this tree does pin is the shape the library expects to
consume — the two attribute names and their permission model, recorded in
`lib/src/cuid_util.h`.

## Impact

- **New files**: `drivers/gpu/drm/amd/amdgpu/amdgpu_cuid.{c,h}`,
  `Documentation/ABI/testing/sysfs-driver-amdgpu-cuid`.
- **Modified**: `drivers/gpu/drm/amd/amdgpu/Makefile` (`amdgpu_cuid.o`),
  `amdgpu.h` (embed `struct cuid` in `struct amdgpu_device`),
  `amdgpu_device.c` (call `cuid_sysfs_init()` / `cuid_sysfs_fini()`).
- **Kernel ABI**: three new sysfs files under
  `/sys/bus/pci/devices/<dev>/`. Once upstream, the payload layout, the UUIDv8
  framing and the derivation are frozen — a change to any of them changes every
  identifier already handed out.
- **Crypto dependency**: `crypto/sha2.h`, specifically the synchronous
  `hmac_sha256_usingrawkey()`. That symbol is `EXPORT_SYMBOL_GPL`, which
  collides with the MIT licence on the amdgpu files. Tolerable while the code is
  built into `amdgpu`; it must be resolved before the core is split into a
  standalone `amd_cuid.ko` that AINIC and NPU also register with.
- **Userspace**: the ROCm CUID library (`projects/cuid`) is the intended
  consumer. At the time this change was written it read none of these files and
  recomputed everything itself; wiring it up was tracked separately (T3) and has
  since landed in `pin-cuid-cross-layer-contract` — `CuidDevice` now reads
  `cuid_primary` and `cuid_secondary` as stage 1 of its lookup for every
  component with a PCI routing ID, and stops recomputing where the driver
  answers.
- **Placeholder constants**: `CUID_DEFAULT_SEED` ships as
  `"AMD-CUID-DEFAULT-SEED-v1"` (24 bytes, no NUL), byte-identical to the
  library's. Its final value is an open question (T1) but it is not
  ABI-affecting in the same way — the seed is administrator-provisioned in any
  real deployment, and the default is documented as a placeholder.

### Explicitly out of scope

Each of these is either blocked on an answer or deliberately deferred so it does
not hold up the first posting:

- The auxiliary/temporary CUID construction (S1's 256-bit input structure). Its
  bit ranges do not sum, and it is user-mode work regardless.
- The temporary-CUID fixed key (T2) and the final canonical seed bytes (T1).
- Hoisting the seed to node-wide scope (T4) and persisting it across module
  reload in a UEFI variable (T5) — the GUID, name and attributes must be agreed
  with AINIC and NPU first, and a world-readable efivar is not an acceptable
  store for a secret.
- `AMDGPU_INFO_PRIMARY_CUID` / `AMDGPU_INFO_SECONDARY_CUID` IOCTLs (T7). UAPI
  attracts far more scrutiny than sysfs; bundling risks holding up both.
- Per-partition / XCP `unit_id`, and the SMBIOS/ACPI short-circuit for the
  Platform and CPU component types.
- The hypervisor opt-out raised by PSO (S1 comment 454362121). The `0400`/`0444`
  split answers serial *disclosure*, not cross-instance *correlation*. A module
  parameter is trivial now and an ABI change after upstreaming, so it must be
  settled before posting even though it is not implemented here.
